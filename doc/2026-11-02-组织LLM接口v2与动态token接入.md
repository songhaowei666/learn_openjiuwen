## 背景：openjiuwen 三级模型

```text
1. AsyncOpenAI / httpx     # 真正发 HTTP、拼 URL、带 header、流式解析
2. ModelClient             # 协议适配、鉴权策略、连接池、请求/响应归一化
3. Model                   # 业务统一入口 invoke/stream，不感知网关细节
```

调用链：`Model` → `create_model_client` → 具体 `*ModelClient` → `AsyncOpenAI` / 自建 transport。

参考实现：

- `Model`：`openjiuwen/core/foundation/llm/model.py`
- `OpenAIModelClient`：`openjiuwen/core/foundation/llm/model_clients/openai_model_client.py`
- 动态 OAuth 先例：`OpenAIAccountModelClient` + `OpenAIAccountAuthManager`
- 配置：`ModelClientConfig`（`api_base` / `auth_mode` / `custom_headers`）

## 问题 1：真实路径是 `.../chat/completions/v2`

### 问题

组织接口路径是：

```text
{prefix}/chat/completions/v2
```

不是常见的 `{base}/v1` + SDK 再拼 `/chat/completions`，也不是 `{base}/v2/chat/completions`。

当前 openjiuwen / `AsyncOpenAI` 默认拼法是：

```text
{api_base}/chat/completions
```

仅改 `api_base` 对不上：

| 你设的 `api_base` | 实际请求 |
|---|---|
| `https://gw/...` | `.../chat/completions`（缺 `/v2`） |
| `https://gw/.../v2` | `.../v2/chat/completions`（顺序错） |
| `https://gw/.../chat/completions/v2` | `.../chat/completions/v2/chat/completions`（重复拼） |

`_normalize_openai_base_url` 只剥「以 `/chat/completions` 结尾」的 URL，对 `/chat/completions/v2` 无效。

### 在哪一层解决

**第 2 层 `ModelClient`（URL 拼装）**。

- `Model`：不动。
- `AsyncOpenAI`：不要指望靠“把完整 path 塞进 base_url”糊弄过去。
- 配置层不能只靠现有 `api_base` 表达该 path。

### 如何解决

1. 在 org `ModelClient`（或现有 `OpenAIModelClient` 的可配置扩展）中显式拼路径：

   ```text
   api_base = https://gw.example.com/<prefix>   # 不含 chat/completions/v2
   completions_path = chat/completions/v2
   → POST {api_base}/{completions_path}
   ```

2. 协议体若仍是 OpenAI chat/completions JSON + SSE，body/流式解析继续复用现有逻辑；必要时走 httpx 直 POST（类似亲和网关 raw HTTP），而不是默认 `chat.completions.create` 路径。

3. 可选：增加 `endpoint_profile` / org provider 别名，业务只写组织 provider 名。

## 问题 2：鉴权不带 Bearer

### 问题

组织鉴权**不是** `Authorization: Bearer <key>`，而是自定义头（具体头名待确认）。

默认 `auth_mode=ApiKey` 会让 SDK / Client 带上 Bearer。

### 在哪一层解决

**第 2 层 `ModelClient` + `ModelClientConfig` 的鉴权模式**。

- 已有能力：`LLMAuthMode.CustomHeaders` / `NoneAuth`
- 先例：`AscendAffinity` 使用 `auth_mode=CustomHeaders`

### 如何解决

```text
auth_mode = CustomHeaders
api_key   = ""                          # 留空，避免拼 Bearer
custom_headers = { 静态头... }          # 仅放不变的头
```

Client 侧已有 omit 逻辑：`CustomHeaders` 且 `api_key` 为空时，剥掉 `Authorization`（`_should_omit_authorization` + httpx event hook）。

动态凭证不要写死在静态 `custom_headers`（见问题 3）。

## 问题 3：需要动态 token

### 问题

Token 会过期，需要按请求解析 / 刷新 / 失败重试，不能配死在配置里，也不能让业务每次手动塞 header。

### 在哪一层解决

拆成两块，**都不要进 `Model`**：

| 组件 | 层级 / 位置 | 职责 |
|---|---|---|
| `OrgAuthManager` | extensions / org 适配包 | 取 token、缓存、过期、刷新、加锁；对外 `resolve_token(force_refresh=False)` |
| 注入与 401 重试 | **第 2 层 `ModelClient`** | 每次 invoke/stream 前取 token → 写入本次请求头；401/403 则 `force_refresh` 再打一次 |
| `Model` | 第 3 层 | **不管** token |
| 静态 `api_key` / `custom_headers` | 配置 | 只放不变的东西 |

对齐先例：`OpenAIAccountAuthManager` + `OpenAIAccountModelClient._invoke_once`（先 resolve，失败 force_refresh）。

### 如何解决

```text
OrgAuthManager          # 刷新/缓存动态 token（非 Bearer 同样适用）
        ↑
OrgModelClient          # path=chat/completions/v2 + 每次请求注入自定义头
        ↑
Model                   # 业务入口不变
```

建议行为：

1. **Manager**：只暴露 `resolve_token(force_refresh=False)`；内部处理 skew、缓存、并发刷新。
2. **ModelClient**：发请求前取 token，写入组织要求的 header 名；鉴权失败有限次刷新重试。
3. **禁止**：
   - 业务侧每次 `model.invoke(..., custom_headers={token})`
   - 把会过期的 token 写进静态 `custom_headers`
   - 改共享 `AsyncOpenAI` 全局 `api_key` 做刷新（易串租户，且你们不用 Bearer）
   - 把刷新逻辑塞进 `Model`

## 总览：三件事各自落哪

| 问题 | 落层层 | 解法要点 |
|---|---|---|
| 路径 `chat/completions/v2` | ModelClient（URL） | 显式 `completions_path`，勿滥用 `api_base` |
| 非 Bearer 鉴权 | ModelClientConfig + ModelClient | `auth_mode=CustomHeaders`，`api_key` 留空 |
| 动态 token | AuthManager + ModelClient | Manager 管刷新；Client 管注入与 401 重试；Model 不动 |

协议兼容时：**尽量不新造第 3 层 API**；优先 org `ModelClient`（外挂 AuthManager）。协议不兼容时再考虑独立 transport，仍保持 `Model` 入口不变。
